Wave prediction feedback and decoder timestamp audit
2026-10-23; read-only source and shipped-binary inspection

Scope and conclusion
Valid Wave display predictions do affect future SSVR tracking prediction and timestamp labels through the latency average. No direct dependency on that prediction was found in SSVR's render-loop deadline or decoder queue target. The timestamp labels also reach Android's explicit output-surface timestamp API in the exact deployed Rust core. That API call alone does NOT establish that this ImageReader output waits until that timestamp. No causal explanation of repeated images is proven by this audit.

Critical SurfaceView-versus-ImageReader limitation
Official reference: https://developer.android.com/reference/android/media/MediaCodec#releaseOutputBuffer(int,%20long)
The documentation describes output timestamp assignment generally but promises VSYNC scheduling specifically under SurfaceView specifics. This decoder uses ImageReader::new_with_usage at platform/android.rs:549, not SurfaceView. Therefore timestamp propagation is confirmed; an output hold until the future ID is NOT confirmed for this consumer. No OEM MediaCodec/ImageReader implementation was traced in this bounded audit.
The local NDK header NdkMediaCodec.h:320-332 likewise describes updating the surface timestamp and returning the buffer for rendering; it points to the Java reference for details.

Queue and render-loop paths
platform/android.rs:594 uses acquire_latest_image, which can discard older images. Its listener enqueues decoded images, keyed by returned image timestamp. decoder_queue.rs:64-84 applies occupancy-based dropping and pops available images; it has no display-prediction deadline.
decoder.rs:157-173 retrieves a decoded lease and exact metadata. cpp_main.cpp:1047-1075 further requires a matching retained Wave tracking sample and current reference-space origin. Empty queues or rejected metadata/poses reuse the previous complete image/pose pair. A repeated-image count does not identify which of these paths caused reuse.
android/app/src/main/java/alvr/client/VRActivity.java:693-738 renders then chooses runtime pacing or nextRenderDelayMs; lines 839-859 use refresh rate and monotonic uptime. No use of the measured total latency or predicted display timestamp was found in that deadline.
WVR_SubmitFrame itself can block inside vendor code; this source audit does not rule out internal runtime behavior affected by the patched cap.

Interpretation of live trials
The first cap60 interval had more repeated images than the first control interval, but a second cap60 interval initially had almost none. These observations do not support attributing the first repeat-rate difference to the cap. The matched repeated trials, complete duration, startup conditions, and any thermal/clock/phase differences must be retained in the final report.
Proven direct effect: restored predictions supply valid latency samples and update the prediction average more often.
Proven downstream path: that average controls future pose horizons and source/frame timestamp labels, which reach the codec output-surface timestamp call.
Unproven: whether those changed timestamps delayed ImageReader delivery, or caused any specific repeat-rate difference.
Possible further evidence, without changing timestamp units: record actual prediction offset, frame_id minus monotonic now at codec release, ImageReader arrival delay, queue occupancy/drop counters, and image rejection reason in a separate controlled diagnostic if required. Keep the present cap A/B pair unchanged.
